# Видеоредактор Маркаряна

Telegram-бот принимает видео **только документом**, готовит MP4 и обложку,
публикует в `/video` и на нескольких выбранных страницах сайта. Пересборка
для публикации не нужна. Все разрешённые участники имеют одинаковые права.
Существующие видео сайта остаются в прежних блоках; новые выводятся в блоке
«Видео врача» перед контактами, а в `/video` — перед прежними роликами.

## Локальная настройка

Нужны Node.js **22.13+** (рекомендуется 24 LTS), FFmpeg с libx264
и ffprobe в PATH. WebP-обложки делает Sharp; встроенный `node:sqlite` не требует отдельного драйвера.

1. Скопировать `.env.bot.example` в `.env.bot.local`.
2. Вписать токен и разрешённые числовые Telegram ID через запятую. Список
   поддерживает любое число участников, включая трёх и более. Пустой список
   закрывает всё управление; `/id` доступен каждому только для получения
   собственного ID. Автоматической регистрации первого посетителя нет.
3. Указать общий абсолютный `VIDEO_DATA_DIR` для сайта и бота. Для локальной
   работы подойдёт `<checkout>/private/video-library`; на сервере каталог
   должен находиться **вне папки релиза**, например `/var/lib/dr-markaryan/videos`.
   Эту же переменную добавить в окружение процесса Next.js.
4. Запустить локальный Telegram Bot API, затем `npm run bot:start`.

Токены и реальные ID не коммитить. `.env.bot.local` исключён из Git.
Бот не выводит адреса Telegram API и пути, содержащие токен, в ошибки.

## Крупные исходники

Обычный облачный Bot API разрешает скачивание только до 20 МБ. Для исходников
с телефона нужен [локальный Telegram Bot API](https://core.telegram.org/bots/api#using-a-local-bot-api-server).
Его собрать по [инструкции проекта](https://github.com/tdlib/telegram-bot-api#installation),
запустить с `--local --http-ip-address=127.0.0.1 --http-port=8081`.
Нужны собственные `api_id` и `api_hash` из `my.telegram.org`; это отдельные
реквизиты приложения, не токен бота. Хранить их в закрытом окружении сервиса.

При переносе уже работающего облачного бота сначала вызвать `logOut` на
облачном API согласно документации Telegram. При первом запуске нового
бота этот шаг не требуется. Webhook должен быть отключён: бот использует
long polling и не удаляет накопленные обновления при запуске.

`TELEGRAM_API_FILES_DIR` — корень данных локального Bot API. Бот должен иметь
доступ на чтение к файлам внутри него (при контейнеризации нужен общий том).
Пути из `getFile` проверяются через realpath и не могут указывать за пределы
этого корня. API слушает только loopback, публичный порт для него не нужен.
Облачный режим допускается явно через `TELEGRAM_API_URL=https://api.telegram.org`,
при этом лимит автоматически снижается до 20 МБ.

По умолчанию бот принимает файлы до 2 000 МБ, длительностью до двух часов и
разрешением до 8192 по каждой стороне. `VIDEO_MAX_BYTES` меняет лимит размера.
Имена и MIME не считаются доказательством формата: содержимое проверяет ffprobe.
Обработка идёт последовательно, MP4 — H.264/AAC, до 1080 по каждой стороне,
30 кадров/с. Автоматически создаются обычная и размытая WebP-обложки.
Оригинал копируется во временный файл и удаляется после обработки; исходник
может оставаться в кеше самого локального Bot API — его хранение обслуживается отдельно.

## Публикация и управление

`/new` → документ → название → описание или `/skip` → страницы с галочками →
предупреждение о кадрах операции → обложка и карточка → «Опубликовать».
Если обработка ещё идёт, кнопка публикации появится после «Проверить готовность».
Главная, разделы и услуги берутся из реестров сайта; «Видео» обязательно,
контакты и юридические страницы не предлагаются.

`/videos` показывает все ролики команды с постраничной навигацией. Можно
менять текст, размещение и предупреждение, снимать публикацию и возвращать её.
Нажатие «Сохранить изменения» необходимо для изменения опубликованного ролика.
Конкурирующее сохранение другим участником требует заново открыть карточку,
чтобы не затереть его изменения. В записи сохраняются ID автора и последнего
редактора. `/continue` возобновляет текущий шаг после перезапуска.

Черновики, исходники и JPEG-превью не имеют публичных URL. Маршрут
`/media/videos/<id>/video.mp4` поддерживает GET, HEAD и Range для перемотки,
проверяет статус публикации при каждом запросе и запрещает кеширование.
После снятия публикации **новые** запросы к медиа получают 404; уже полученные
посетителем данные и уже начатую загрузку отозвать нельзя. Для чувствительных
роликов публичный постер размывается; видео запускается после подтверждения.

## Orange Pi и сайт на разных серверах

`VIDEO_SITE_SSH_HOST`, `VIDEO_SITE_SSH_USER`, `VIDEO_SITE_SSH_IDENTITY` и
`VIDEO_SITE_SSH_KNOWN_HOSTS` включают удалённую публикацию. Приватный ключ
создаётся на Orange Pi и не переносится на сервер сайта. Ключ на стороне
сайта разрешает только `site-receiver.py` через forced command с `restrict`;
обычная оболочка, SCP и проброс портов запрещены.

Приёмник работает отдельным пользователем без sudo, пишет только каталог
видео, проверяет имена, размер и SHA-256 файлов и допустимые страницы сайта.
MP4 и обе обложки передаются до атомарного изменения записи в SQLite.
Источник Telegram и внутреннее состояние диалога на сайт не передаются.
Сайт и приёмник используют один `VIDEO_DATA_DIR` на сервере сайта.

Кнопка публикации сначала сохраняет задание на Orange Pi. Подтверждение со
ссылками приходит только после ответа сайта; это относится также к правкам
и снятию публикации. При разрыве связи задание повторяется, старые версии
не могут отменить более новые правки. Пока идёт передача, карточка показывает
«Изменения передаются на сайт». Доступ к серверу не требует Telegram ID
участников; список пользователей бота настраивается независимо.

## Сервер и обслуживание

В `dr-markaryan-video-bot.service.example` — шаблон systemd; перед установкой
подставить фактического пользователя, Node и каталог приложения. Каталог
данных создать заранее, дать пользователю бота запись, процессу сайта — чтение
БД и медиа. Из-за UMask=0077 для разных пользователей потребуются ACL.
Для чтения SQLite WAL процессу сайта также нужны права на файлы `-wal`/`-shm`
(проще использовать одного сервисного пользователя).

Запускать только один экземпляр бота на одном сервере. PID владельца хранится
в SQLite под транзакцией; после аварийного завершения задания `processing`
снова попадают в очередь. При остановке сервис ждёт завершения текущей обработки.
Шаг диалога, offset и очередь ответов фиксируются одной транзакцией. Сбой
Telegram повторяет доставку ответа, а не ввод пользователя в следующем шаге.
Повторный документ из того же сообщения не создаёт копию. Повторное нажатие
публикации не публикует второй ролик. При аварии непосредственно после отправки
ответ может прийти повторно; состояние публикации при этом не дублируется.

В резервную копию включать весь `VIDEO_DATA_DIR`. Для согласованной простой
копии остановить бот, скопировать каталог вместе с SQLite, WAL и SHM, затем
запустить снова; либо использовать SQLite online backup и отдельную копию медиа.
Контролировать свободный диск, состояние сервиса и записи «Ошибка обработки»
в `/videos`. Новые публикации не меняют Git и не запускают deploy workflow.

Проверки: `npm run bot:test`, `npm run check:build`, затем `npm run bot:test:site`.
Тесты используют временную
SQLite и подставной Telegram; тест кодирования использует локальный FFmpeg.
Реальный запуск потребует токена, разрешённых ID, локального Bot API и настройки
одного `VIDEO_DATA_DIR` в обоих сервисах. До этого функциональность проверяется локально.
